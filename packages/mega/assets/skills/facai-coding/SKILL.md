# 计划编码实现

依据 `docs/plans/{序号}-{名称}/` 下的计划文档，将伪代码落地为可运行代码，并自动调用 facai-selfcheck 闭环验证。

## 定位

流水线三件套的中间环节：

```
facai-plan   生成计划（伪代码 + 接口定义 + 调用关系）
    │
    ▼
facai-coding 执行计划（本技能）  ← 伪代码 → 可运行代码 + 自检闭环
    │
    ▼
facai-selfcheck 验证代码（依赖红线 + 编译 + 测试 + 契约）
```

---

## 工作流程

### 第零步（强制）：阅读核心规则与架构

> ⚠️ **强制前置**——跳过此步将导致代码违反项目红线，触发 facai-selfcheck FAIL。

务必完整阅读以下文档，建立约束意识后再开始任何编码工作：

1. **`ARCHITECTURE.md`**：项目架构全景——模块边界、依赖方向、分层架构，新增代码的 import 必须落在合法依赖方向内
2. **`coding-rule.md`**：编码红线——依赖方向、import 与可见性、错误处理与日志、数据结构约定、配置、命名、复用，每一条都是 facai-selfcheck 的检查项
3. **`domain-extra-rule.md`**（若存在）：领域专用红线——项目特有的架构约束

> 💡 **可按需**检索 `spec/` 下的行为契约文档，确保实现与现有行为契约一致。

### 第一步：理解计划

1. **读总览**：读 `docs/plans/{序号}-{名称}/README.md`，掌握目标、架构总览、步骤索引表、依赖关系图
2. **读步骤文件**：读用户指定的步骤文件（如 `01-core-types.md`），理解：
   - 要实现的文件清单和职责
   - 核心类型定义（数据结构字段、接口、函数签名）
   - 模块间调用关系和数据流
   - 设计要点（决策理由和边界情况）
3. **确认前置依赖**：查看步骤头部的 `> 依赖：` 标注，确认前置步骤已完成

### 第二步：理解现有代码

实现前必须阅读相关现有代码，确保新代码与既有架构对齐：

1. **模块入口**：读目标模块的入口文件，了解已有子模块登记和对外可见面
2. **依赖配置**：确认项目依赖配置（如 `Cargo.toml` / `package.json` / `pyproject.toml`）已声明所需的依赖
3. **测试规范**：阅读 `test-rule.md`（测试归口、按功能点拆分）
4. **风格参照**：读 1~2 个同模块的现有文件，对齐注释密度、命名惯例、代码组织方式

### 第三步：建立任务清单

用 TodoWrite 将实现拆为可追踪的子任务（3 步以上时），典型拆分：

```
- 创建源文件 A（类型/接口定义）
- 创建源文件 B（依赖 A 的类型）
- 在入口文件登记新模块
- 创建单元测试文件并登记
- 编译 + 测试验证
```

### 第四步：按计划实现代码

将计划中的伪代码落地为真实实现，遵循项目编码规范（完整规则见 `coding-rule.md` 和 `domain-extra-rule.md`）。

> 以下为通用原则，具体语法（import 方式、错误处理、命名风格等）以 `coding-rule.md` 为准——该文件由 init 向导根据项目语言生成。

**模块与 import**
- 新增文件必须在对应入口文件中登记
- 跨模块引用遵守项目的依赖方向（见 `ARCHITECTURE.md`）
- 内部实现不滥用可见性修饰符，由入口文件决定对外可见面

**类型与命名**
- 遵循项目语言的命名惯例（见 `coding-rule.md`）
- 序列化标注需显式指定（如需要对齐外部协议结构）

**错误与日志**
- 错误按项目语言惯用的方式向上传播，不要用会导致 panic/崩溃的操作（测试代码除外）
- 日志用项目的日志库，不用裸打印（CLI 占位输出除外）

**注释**
- 公开函数必须有文档注释，说明用途和关键参数
- 模块级注释描述文件/模块职责
- 注释语言遵循项目约定

### 第五步：编写测试

遵循 `test-rule.md`：

- 测试归口到项目的测试目录下（具体路径见 `test-rule.md`），按功能点命名文件
- 入口文件仅作登记，不放测试函数
- 测试函数命名描述被测行为
- 纯逻辑优先单测；需活体资源（DB/Redis/外部 API）的逻辑标记跳过或放入临时目录
- 复用 fixture，禁止每个测试重复构造完整结构

### 第六步：编译与测试验证

```bash
# 1. 编译通过（命令从 pipeline.config.yaml 的 commands.build 读取）
{build_command}

# 2. 单元测试通过（命令从 pipeline.config.yaml 的 commands.test 读取）
{test_command}
```

编译或测试失败时立即修复，修复后重新运行，循环直到通过。

### 第七步：自检闭环（调用 facai-selfcheck）

编码完成且编译 + 测试通过后，**必须调用 facai-selfcheck 技能**执行代码自检：

```bash
python .agents/skills/facai-selfcheck/scripts/selfcheck.py
```

- **有 FAIL**：立即订正，订正后重新运行，循环直到 FAIL = 0
- **有 WARN**：判断是误报/占位还是需修复——需修复的立即订正，确认为误报的在汇报中说明理由
- **全部通过**（FAIL = 0 且无待处理 WARN）后进入第八步

### 第八步：交付汇报（不提交）

facai-selfcheck 全部通过后，向用户汇报实现结果与验证情况（改动文件、测试/自检结论、与计划的偏差等）。

**不执行 `git add` / `git commit` / `git push`**——代码提交由用户自行决定或另行指示，本技能不自动提交。

## 实现原则

1. **计划是契约，不是建议**：计划文件中的接口、数据结构字段、函数签名是后续步骤依赖的契约，实现时不得擅自更改签名或删减字段。若发现计划有误或遗漏，先向用户说明再调整。

2. **计划到代码的边界**：计划给的是伪代码（函数体用占位符表示），编码阶段填充真实逻辑。如果计划中的伪代码已有完整字段定义和注解，直接采用而非重新设计。

3. **一次实现一个步骤**：按用户指定的单步实现，不跨步骤抢跑。每个步骤是独立交付单元。

4. **能复用不造轮子**：优先复用项目已有代码和标准库。引入新依赖前先确认项目配置是否已声明。

5. **编译验证是硬门槛**：编译必须零错误，测试必须全绿，才能进入自检环节。

---

## 质量检查清单

实现完成后逐条确认：

- [ ] **计划完整性**：计划中列出的所有文件都已创建，所有类型/函数都已实现
- [ ] **模块登记**：新增的源文件都在对应入口文件中登记
- [ ] **签名一致**：实现的接口、数据结构字段、函数签名与计划一致
- [ ] **依赖方向**：无反向依赖（遵守 `ARCHITECTURE.md` 的依赖方向）
- [ ] **领域红线**：遵守 `domain-extra-rule.md` 中的领域约束（若存在）
- [ ] **错误处理**：业务代码无 panic 类操作，错误正确传播
- [ ] **注释规范**：公开项有文档注释，模块有职责说明
- [ ] **测试归口**：测试在项目测试目录下按功能点拆分，不在业务源码散落
- [ ] **编译测试通过**：编译零错误，测试全绿
- [ ] **facai-selfcheck 通过**：FAIL = 0，WARN 已全部确认/修复
