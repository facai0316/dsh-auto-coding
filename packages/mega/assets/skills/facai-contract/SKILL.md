# 行为契约更新

维护 `spec/` 目录下的行为契约文档，并同步 `spec/README.md` 契约索引。

> 契约映射关系由 `pipeline.config.yaml` 的 `spec_mapping` 段配置（init 向导生成）。

## 核心原则

**契约记录「系统怎么表现」，更新必须保留可观测行为保证。**

- 契约与代码冲突时，按 `spec/README.md` §契约优先级处理：契约正确 → 修代码；契约过时 → 先更新契约再调代码
- 契约变更需经确认，变更原因记录在 commit message 中
- 本技能只负责「是否更新 + 怎么更新」的判断与执行，不负责代码实现（那是 /facai-coding 的职责）

## 工作流程

### 第零步（强制）：收集现状

1. 阅读 `spec/README.md`：契约索引与优先级约定
2. 阅读 `decisions/README.md` 索引：确认最新决策（ADR）状态，判断是否有可依据的最新语义
3. 查看本次 git diff（代码或决策变更），列出全部行为变化点
4. 读取 `pipeline.config.yaml` 的 `spec_mapping` 段，获取源码路径 → 契约文件的映射关系

### 第一步：检查冲突

逐项对比变更内容与现有契约，识别冲突。若 diff 无行为变化 → 无需更新，直接结束（检查通过）。

> 检查范围依据 `spec_mapping` 配置：遍历每个映射项，检查变更的源码是否落在映射的 source 路径下，若是则对照对应契约文件。

### 第二步：解决冲突（按用户最新语义）

| 场景 | 处理 |
|------|------|
| 变更来自**最新决策**（ADR 已 Accepted / 用户明确指示） | **直接更新**契约，使其与最新语义一致，不询问 |
| **临时想法 / 未定方案**，但违背既有契约和规则 | **不擅自更新**——先询问用户：确认采纳则更新契约（如需建档先调 /facai-decision），不采纳则保持契约并说明影响 |
| 契约描述与实际实现不一致（契约过时） | 确认过时后更新契约，再修代码（如需要） |
| 信息不足、无法判断是否影响契约 | **询问用户**，按用户要求执行 |

> 询问用户时必须给出选项与影响：更新契约（改 spec 文件）/ 不改（保持现状，注明原因），并说明违背点。

### 第三步：更新契约

1. 根据 `spec_mapping` 定位受影响的契约文件
2. 阅读现有契约上下文，**增量修改**受影响的行为描述（保持 MUST / SHOULD / MUST NOT 术语风格，中文书写）
3. 同步 `spec/README.md` 契约索引（如涉及新文件或索引描述变化）
4. 若更新伴随决策变更，先经 `/facai-decision` 建档

### 第四步：验证

1. 重跑 `facai-selfcheck`：确认 §行为契约同步 的 WARN 已消除（spec 变更后自动识别为已同步）
2. 对照 `spec/README.md` §契约优先级，确认代码侧无需再调整
3. 检查 `git diff spec/` 只包含本次行为的增量变化，无无关改动

## 注意事项

- **确定性缺失由脚本自动补**：运行 `facai-selfcheck` 时，新增标识符未登记会被自动补入 spec 清单（幂等追加、标注「（自动修补）」）；本技能处理的是需要语义判断的更新
- **不替代决策存档**：更新契约若源于新决策，先 `/facai-decision` 建档
- **不替代代码自检**：更新契约后必须重跑 `facai-selfcheck` 验证
- **不强制更新**：无行为变化时检查通过即可，不得为了「同步」而改契约
- **领域规则联动**：若领域专用规则（`domain-extra-rule.md`）涉及行为契约（如事务语义、状态机约束），其变更同样触发契约检查
